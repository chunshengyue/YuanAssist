# 烧烤模式现有已知

更新时间：2026-04-30

## 1. 已确认业务规则

- 本模式所有图像识别统一使用模板匹配，不使用 OCR。
- 不单独判断客人是否存在，只检查客人气泡。
- 上架不需要拖动，点击食材后自动上架。
- 只有交付时需要拖动，把成品拖到客人整张盘区域。
- 交付的拖动语义是：按住第一个坐标，拖动到第二个坐标，然后松开。
- 客人满足需求后，等待一小段时间会出现清理按钮，同时客人离开。
- 清理按钮坐标和餐盘投递坐标相同。
- 清理动作本身不需要再做一次模板匹配；一旦确认到了清理阶段，直接点击对应餐盘坐标即可。
- 每个烧烤架最多可放 3 个食物。
- 第二个烧烤架是否启用，由用户选择。
- 审查策略采用事件驱动；如果距离上次审查超过 1 秒，补一次模板审查。
- 每次审查只截一张图，同时检查 3 个气泡需求和各客人清理状态。
- 所有手势类动作统一额外增加 `200ms` 调度延迟，包括点击和拖动。
- 平时烧烤进度优先靠内存计时维护，异常时再做模板重同步。
- 目前不需要单独处理“烤糊”问题，按较大容错处理即可。
- 客人需求除了食物，还可能包含饮料。
- 饮料也显示在客人需求气泡里，和食物一样需要进入需求识别与 token 调度。

## 2. 状态机骨架

- `GuestSlot`
  - 记录客人当前需求
  - 记录是否已满足
  - 记录是否待清盘
- `DemandToken`
  - 每个客人的每个单项需求拆成一个 token，例如 `G1-牛骨髓`、`G2-广陵山泉`
  - 状态流转：`waiting -> reserved -> cooking -> cooked -> delivered`
- `GrillSlot`
  - 记录当前绑定的 `tokenId`
  - 记录 `foodType`
  - 记录 `startAt / readyAt / burnAt`

## 3. 调度原则

- 交付归属通过 token 绑定解决，不通过全局需求池反推。
- 优先级：
  - 一旦审查发现清理，清理优先级高于所有任务，立即点击对应餐盘
  - 空烤架尽量补满食物，作为第二优先级
  - 已烤好的食物优先交付
  - 已出杯的饮料其次交付
  - 烤架补满后，再开始倒水
  - 距离上次审查超过 1 秒时补审查
- 食物需求和饮料需求共用同一套客人归属模型，但执行动作不同：
  - 食物：点击食材上架，等待固定时长后拖到餐盘
  - 饮料：打开饮料位，选择种类，长按倒水，进入“已出杯待交付”状态，再拖到餐盘

### 3.1 当前确认的执行顺序

1. 先把当前空闲烧烤位尽量补满。
2. 再执行倒水动作。
3. 倒完水后，优先交付已经烤好的串。
4. 串交完后，再移动饮料到餐盘。
5. 然后继续下一轮调度。

### 6.3 饮料执行流程

1. 识别到客人需要某种饮料。
2. 点击饮料位打开种类选择。
3. 点击目标饮料种类。
4. 执行一次倒水按钮模板识别，模板名为 `倒水魂.jpg`。
5. 长按倒水按钮 2 秒。
6. 从饮料成品位拖到目标客人餐盘。

## 7. 推测量

- 食材4、食材5 的 `x` 坐标按前序差值近似外推。
- 餐盘3 / 清理3 的坐标按前序差值外推。
- 气泡3 的中心点按前序差值外推。
- 第二烧烤架第 2、3 个成品拖动起点按第一烧烤架相对位移外推。

这些推测量当前容错较大，可先作为实现基线，后续若补测到更精确值，直接替换配置即可。
